# 五、六大合同逐项审计

## P0-1｜Recognition Runtime Contract

重点审计模型运行及 Native 生命周期。

### A. 模型身份和 Schema

检查：

- Detector。
- Classifier。
- Vision Encoder。
- Mask Decoder。

每个模型必须具有独立身份：

`modelId + modelVersion + modelSha256 + inputSchemaHash + outputSchemaHash + preprocessVersion`

检查：

1. APK 实际模型是否与登记身份一致。
2. ONNX/TFLite 输入输出 Schema 是否真实读取。
3. 动态 Tensor Shape 是否正确处理。
4. 是否存在固定 Shape 错误。
5. 模型 Session READY 是否基于真实 Session 创建。
6. 是否错误地将部分模型 READY 合并为完整 SlimSAM READY。

特别核验 SlimSAM Vision Encoder：

`pixel_values: FLOAT [batch_size, 3, 1024, 1024]`

必须允许动态 batch 维度。

不得仅根据历史模型资料推断当前模型 Schema。

### B. Runtime 生命周期

检查：

- Application 级 Session 所有权。
- 页面退出是否误关闭 Session。
- Activity 重建是否影响 Session。
- Result 导航是否触发资源释放。
- Inference Run 是否有唯一 inferenceId。
- RunOptions 是否按每次推理独立创建。
- 输入输出 Tensor 是否有明确生命周期。
- Native 使用期间是否发生提前释放或复用。

### C. Embedding 并发和缓存

检查：

- Cache Key 是否包含 canonicalPixelSha256。
- Encoder Model SHA 是否参与 Cache Key。
- Preprocess Version 是否参与 Cache Key。
- Input Schema / Shape 是否参与 Cache Key。
- 同一照片并发请求是否合并。
- 新 Attempt 是否可能接收旧 Embedding。
- Decoder 是否可能读取已释放 Embedding。
- 内存压力下缓存是否有正确回收机制。
- 是否存在无界并发。

### D. Native 取消和资源释放

严格区分：

`CANCEL_REQUESTED`

`TERMINATION_REQUESTED`

`NATIVE_CALL_RETURNED`

`SESSION_CLOSED`

`RESOURCE_RELEASED`

检查是否存在以下错误：

- 业务层取消就认为 Native 已停止。
- Thread.interrupt 被当成 Native 强制终止。
- Native 尚未返回就释放 Buffer。
- Native 尚未返回就关闭 Session。
- 旧 Attempt 的迟到回调污染新 Attempt。
- 超时后仍允许旧结果提交。
- 取消后重试时复用不安全资源。

如果 Native Call 卡住，必须确认是否存在：

`NATIVE_CALL_STUCK`

及 Session/Attempt 隔离机制。

### E. 60 秒模型等待

检查整体模型依赖是否有统一 60,000ms Deadline。

禁止：

- 每个子模型完成后重置总 Watchdog。
- 通过串行等待无限延长。
- 将 60 秒模型等待混入 6000ms 视觉时钟。
- 超时后无条件推进 FULL_REVEAL。

### F. 内存与算子归因

区分：

1. RSS/PSS。
2. Native Heap。
3. Native Allocator Trace。
4. ORT Operator Profile。
5. Operator Allocation Attribution。

没有真实 allocator/call-stack 关联时，不允许声称已经找到具体算子的 Native 内存分配量。

输出各模型的：

- Session 创建和释放路径。
- Run 生命周期。
- 输入输出资源所有权。
- 并发策略。
- Embedding Cache。
- 取消链。
- 内存观测能力。
- 已知风险。

## P0-2｜Recognition Result Snapshot Contract

重点审计全局身份一致性和不可变数据链。

### A. ID 体系

检查以下 ID 是否真正独立：

- recognitionSessionId
- attemptId
- photoId
- modelSessionId
- inferenceId
- maskId
- contourId
- fishPathSnapshotId
- snapshotId
- handoffId
- evidenceSessionId

禁止一个通用 sessionId 混用多种业务身份。

### B. PhotoIdentity

必须区分：

- sourceBytesSha256
- canonicalPixelSha256

检查照片归一化、EXIF、Bitmap 转换、模型输入、Mask、Contour、P*、FishPath 是否使用同一规范像素身份。

特别检查不同模块是否分别使用 JPEG SHA 和 Bitmap Pixel SHA，却都写入同一个 photoSha256。

### C. MaskIdentity / ContourIdentity

检查 Mask 是否绑定：

- PhotoIdentity。
- Model Identity。
- Prompt Identity。
- Mask SHA256。
- Mask Version。
- Geometry Version。
- Coordinate Space。
- Width / Height。

Bitmap generationId 只能作为缓存提示，不得作为持久身份。

Contour 必须从当前 Attempt 的可信 Mask 派生。

### D. FishPathSnapshot 创建时机

这是本轮 P0 必查项。

合同要求：

Stage05 `PATH_TO_FISH`：

1. 真实 FishPath 注册。
2. Controller 接受 PATH_BOUND。
3. SessionStore 接受相同 Path Identity。
4. 立即创建并冻结 RecognitionFishPathSnapshot。

Stage10 ORB_RETURN 只能消费原始快照。

必须检查：

- Path 是否真正注册。
- Controller 和 Store 是否双向接受。
- 是否存在事件先后顺序问题。
- 是否出现 PATH_BOUND 但 Snapshot 没有创建。
- 是否存在路径创建后又被覆盖。
- Stage10 是否重新创建 FishPath。
- RETURN 是否使用相同 pathId、segments、P* 和 geometryVersion。

### E. RecognitionResultSnapshot 提交

检查：

- 模型分支是否全部进入终态。
- Mask 是否真正终态。
- FULL_REVEAL 是否要求 TRUSTED Mask。
- ORB_ONLY 是否要求 Mask 已终态。
- MASK_PENDING 是否可能提前成为 ORB_ONLY。
- CLASSIFICATION_FAILED 是否可能显示虚假鱼名。
- 一个 Attempt 是否可能提交多个 Snapshot。
- Snapshot Commit 后是否仍然原地修改。

必须区分：

`FULL_REVEAL`

`ORB_ONLY`

`CLASSIFICATION_FAILED`

`FAILED`

`TIMED_OUT`

`CANCELLED`

### F. 异步乱序

检查每一个关键回调是否验证：

`recognitionSessionId + attemptId + photoId`

旧 Attempt 回调必须隔离。

输出完整身份流转图：

`Photo → Model → Mask → Contour → P* → FishPathSnapshot → ResultSnapshot`

FULL_REVEAL 必须消费 Stage05 冻结的 FishPathSnapshot。

检查：

- 原始 pathId。
- 原始 segments。
- P*。
- Mask SHA。
- Geometry Version。
- RETURN 路径。
- Controller 接受事件。

禁止使用新建默认路径 ID 冒充原路径。

### B. Result Geometry

检查 ResultGeometryReceipt 是否独立于 RecognitionResultSnapshot。

必须区分：

- Layout Geometry READY。
- Hero Raster READY。
- GPU Render Geometry。
- PixelCopy Screen Geometry。

不能因为 Hero Raster 异步加载而错误阻塞已完成的布局几何。

也不能用 Layout Bounds 冒充真实屏幕像素证据。

### C. Host Pre-mount

检查 Result Host 是否可以提前挂载并测量 Geometry。

必须区分：

- Host Mounted。
- Geometry Ready。
- Scene Ownership Transfer。

Host Mounted 不等于 Result 接管。

### D. Photo Settle

检查：

- Processing Source Geometry。
- Result Hero Target Geometry。
- PhotoIdentity。
- canonicalPixelSha256。
- Transform。
- Crop。
- Bounds。
- Geometry Version。
- 完成 Receipt。

必须是同一张照片的连续变换。

### E. Handoff Envelope / ACK

检查 Producer 与 Consumer：

- Envelope 是否完整。
- Consumer 是否校验 Snapshot Hash。
- Species 与 Glyph 是否一致。
- Mask / Contour / Path Identity 是否一致。
- Geometry 是否有效。
- 事件序号是否正确。
- 幂等是否有效。
- Consumer 是否真实生成 ACK。

禁止把 Navigation Requested、ResultScreen Composed 或 Host Mounted 当作 ACK。

### F. Scene Ownership

13.3 ACK 之前：

Processing Scene 是可见 Owner。

13.3 Consumer ACK 之后：

Result Scene 原子接管。

不得同时由两个 Host 重复绘制同一 Photo/Glyph/Orb 层。

检查 13.1–13.5 是否真正按序执行。

只有 13.5 Consumer 接受后，才允许：

`resultSceneStable=true`

`Playback COMPLETED`
